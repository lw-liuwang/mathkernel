# 首轮 CPU 实验规格（待用户确认）

本轮要验证 MathKernel 的数学变换及成本预测，是否能指导本机 CPU 上的实际优化。实验基于已发布的 v0.3.0，保留原始测量、失败尝试和模型与实测的偏差。

用户已授权补充定义与方法；本文件是补充后的完整规格，尚未获得任务确认。两个 `task.json` 均应保持 `needs_confirmation`。确认前不运行候选评价，不填写 `review.json`，不报告候选已验证或已验收。

## 数学语义、基线与变换

| 实验 | 计算与基线 | 允许的变换 | 正式成本评价规模 | 补充实测规模 |
| --- | --- | --- | ---: | --- |
| 逐元素融合 | `t1=a*b; t2=t1+c; y=t2*d`，三次完整遍历、两个中间数组 | 融合为 `y=(a*b+c)*d`，逐元素运算顺序不变 | n=4,194,304 | n=1,024、262,144 |
| 矩阵乘 | `C=A*B`，按 i,j,k 循环，每个输出从零开始按 k 递增累加 | 按 ii,jj,kk,i,k,j 分块，边界裁剪，每个输出的 k 顺序不变 | n=512 方阵 | n=64、256、257 方阵 |

输入为连续、互不重叠的 FP64 数组，矩阵按行存储。基线是本目录的简单 C 实现，不代表成熟数学库。只比较这些明确基线与候选，不声称超过 BLAS 或其他设备。

Lean 模型采用精确有理数：有限 FP64 输入均可精确表示为有理数。融合模型比较分阶段与融合后的表达式；矩阵乘模型证明将连续 k 索引分组后，左折叠的元素及顺序保持不变。该证明不依赖加法结合律，也不改变每个输出的累加次序。

当前工具不能直接评价含 Lean 非可计算实数定义的模型，最小复现见 [准备阶段观察](observations/README.md)。精确有理数模型不模拟 IEEE 754 的逐步舍入，也不证明编译后的 C 程序；这两项由数值检查和实现核对另行验证。任务的正式资源与目标检查针对表中的代表规模，补充规模用于观察实现对规模和边界的敏感性；其性能测量不属于额外的正式资源验收。

## 硬件与成本模型

硬件为本机 Core Ultra 5 125H，运行在 WSL2。标定和后续计时固定在逻辑 CPU 0；宿主机调度、频率和后台负载仍可能影响结果。编译器为 GCC 15.2.0，公共选项为 `-O3 -std=c11 -march=native -fno-fast-math -ffp-contract=off -Wall -Wextra -Werror`。基线与候选使用一致选项，不允许浮点重结合或融合乘加。

[environment.json](environment.json) 保存设备信息、编译命令、源文件与二进制摘要及全部标定样本。标定先预热一次，再取七次样本的中位数：

- 计算标定使用八路独立 FP64 乘加递推，每轮计 16 次独立运算，有效速率为 **9,083,202,562 FLOP/s**。
- 流式标定读一个数组、写一个数组，每个元素计 16 字节；两个数组合计 256 MiB，有效负载速率为 **20,634,462,533 字节/s**。
- 以上是特定程序的有效速率，不是厂商峰值，也没有通过性能计数器测量 DRAM 流量。后续不为贴合结果而重新调整已确认参数。
- 采用 **32 KiB** 快速存储预算；这是在客体报告的 48 KiB L1 数据缓存内预留余量的模型假设，不表示实际分配了缓存分区。

通用工具计算各阶段 `max(F/P,Q/B)` 后求和。CPU 任务沿用协议中的 `hbm_bytes` 字段，但其含义为模型慢速层的负载字节数。未建模缓存命中、写分配、预取、组相联冲突、循环开销、向量化和调度，报告须讨论这些限制对预测的影响。

| 实现 | FLOP | 模型负载字节 | 快速存储预算（字节） |
| --- | ---: | ---: | ---: |
| 融合基线，每个阶段（共三阶段） | n | 24n | 24 |
| 融合候选 | 3n | 40n | 40 |
| 矩阵乘基线 | 2n³ | 16n³+8n² | 24 |
| 分块矩阵乘，块宽 b | 2n³ | 16n²⌈n/b⌉+8n² | 24b² |

融合的中间数组归入慢速存储，流量按每阶段两次读取、一次写入计算。矩阵乘分块模型假定 C 块在快速存储中完成累加，每个 A/B 块对一个 C 块只装入一次；尾块裁剪。它描述理想的数据复用，不保证 C 实现或缓存确实达到该流量。快速存储计数覆盖三个方块；边界以完整块作为保守上界。数学正确性证明与这些执行成本假设应分别判断。

## 目标、预算与停止条件

两个任务分别最小化 `estimated_seconds`，要求相对基线严格改善，`minimum_reduction=0/1`。每个任务最多评价 **12 个候选**，不设置墙钟探索预算；单次 Lean 命令默认超时 120 秒。整条变换链算一次候选，包括开始执行后失败或超时的尝试。

融合使用 `fuse` 规则。矩阵乘探索块宽 8、16、32，并保留块宽 64 超过快速存储预算的诊断；需要时可在同一预算与已确认规则内选择其他参数。较大块即使降低模型流量，也不能绕过资源限制。中间变换无需降低成本，最终候选必须通过可行性与目标检查。

达到模型目标后，可以在剩余预算内比较已定义参数的实测效果。最终报告分别指出模型预测最优和实际最快的已探索候选，不声称全局最优。预算耗尽或没有合格候选时保留失败原因，不擅自放宽目标、改模型或追加预算。模型、硬件参数、目标、基线或预算改变后重新确认。

## 数值检查与计时方法

- 固定随机种子 `20261123`，常规输入分布为 `[-1,1]`，另外检查零值、正负值和可精确表示的二进制分数。融合覆盖 n=0、1、17、1,025；矩阵乘覆盖 n=0、1、3、17、65，以及 257、512 的尾块和大规模场景。
- 融合基线先对照精确有理数表达式；一般浮点输入再对照精确表达式的高精度参考，绝对容差为 `16*ulp(1)`。矩阵乘使用零矩阵、单位矩阵及 `math.fsum` 点积参考；绝对容差为 `8*ulp(1)*max(1,n²)`，大规模采用固定的 64 个输出坐标抽样。
- 所有候选另与基线逐元素比较；因运算顺序保持不变，要求输出字节一致，包含零的符号。拒绝出现非有限输出的结果。保留最大绝对误差、最大相对误差以及检查范围；参考值为零时单列绝对误差。
- 每个计时配置预热五次，随后交替测量基线和候选，奇偶轮交换执行顺序，至少保留 20 对样本。计时排除编译、输入构造、分配、数值检查和结果整理，包含算法所需的输出初始化。
- 采用 C 内部计时和批量调用；每批自适应到不少于约 20 ms，记录批量次数，避免 Python 调用开销主导小规模测量。使用已预分配的固定数组重复运行，不人为刷新缓存；报告说明这是重复调用场景。
- 保存每次耗时、中位数、四分位距和配对加速比。只有数值检查通过才报告性能比较；结果波动跨越无加速时如实标记收益不明确，不以最小耗时替代全部样本。

已完成的准备检查见 [preparation.json](preparation.json)：融合基线通过精确表达式、零值、抵消和随机输入检查，最大绝对差约 `2.22e-16`；矩阵乘通过零、单位、随机矩阵检查，对 `math.fsum` 的最大绝对差约 `4.44e-15`。两个任务的定义、规则和实际基线证明均可编译；`task rules` 的状态仍为 `not_run`，候选证书和最终验收尚未运行。候选评价次数为零，没有用户确认记录。
